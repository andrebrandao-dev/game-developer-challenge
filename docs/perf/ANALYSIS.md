# Performance analysis

How to read [REPORT.md](REPORT.md) (generated by `pnpm perf`) and what the
memory investigation found.

## Method

- **Build:** production (`vite build`), served by `vite preview`.
- **Browser:** full Chromium in new-headless mode (real `requestAnimationFrame`
  scheduling and GPU rasterisation via ANGLE/Metal), not the lightweight
  headless shell used by the E2E suite.
- **Reference environment:** Apple M2 (8 cores, 16 GB), macOS 26, Chromium 156,
  1920×1080 at devicePixelRatio 1. The full environment is in each report.
- **Match configuration:** 180 s session with a **1 s spawn interval**, the
  heaviest enemy pressure allowed in Options, so the active cap of 8 enemies is
  reached within seconds. Seed 2026. The player's health is raised so the
  match lasts the full 3 minutes (a balancing override, not a rule change).
- **Pilot:** a script holding real keys: always sailing and firing the bow
  cannon, weaving left/right, firing alternating broadsides.
- **Frame metrics** come from the game's own `FrameStats` (preallocated typed
  arrays, no allocation per frame), recorded only during active play:
  - *frame time*: the Pixi ticker delta between frames;
  - *CPU work*: time from the start of our ticker callback to the end of Pixi's
    render callback, i.e. simulation + scene update + render submission.

## Results (reference run)

| Metric | Value |
| --- | --- |
| Average FPS | **60.0** |
| p95 frame time | **16.7 ms** (max 16.8 ms, 0 % of frames over 17.7 ms) |
| CPU work per frame | 1.04 ms avg, 1.7 ms p95, 4.9 ms max |
| Entities | up to 9 ships + 7 projectiles in flight; 50–150 live particles |

**Reading.** Frame times are locked to the display's 60 Hz vsync, so they show
that the target is met, not how much headroom exists. The CPU work metric
answers that: about 1 ms of a 16.7 ms budget (≈ 10× headroom on this machine),
and the worst frame used under 5 ms. One earlier run showed a single 83 ms
frame at the very start of the match. It did not reproduce; it matches
first-use shader compilation and texture upload. Uploading atlases during
loading would hide it if it showed up on slower devices.

**What keeps it cheap.**
- Fixed-step simulation with small, bounded entity counts (spawn cap,
  projectile range/lifetime, particle cap of 900).
- Static islands rendered once into a texture (`cacheAsTexture`).
- Pooled sprites for projectiles and particles; health-bar fill textures
  cached per pixel width.
- React is not involved per frame: the HUD store notifies only when a
  displayed value changes (≈ 1/s).

## Memory investigation

The report's memory section measures the JS heap after 5 cycles of
start → play 20 s → exit, after two forced garbage collections:

```
baseline 7.12 MB → 8.59 → 8.85 → 9.08 → 9.18 → 9.35 MB
DOM nodes 89 → 94 (stable)    JS listeners 184 → ~190 (stable)    canvases 0 after every exit
```

The first cycle's +1.5 MB is expected one-time warm-up: atlases decoded and
cached in Pixi `Assets` (reused by every later match), shader programs
compiled, modules for the battle screen initialised.

Because the later cycles still grew (≈ 0.1–0.25 MB each), I investigated
further:

1. **Longer run.** 12 cycles: 8.21 → 8.49 → 8.76 → 8.86 → 9.06 → 9.11 →
   9.16 → 9.21 → 9.51 → 9.54 → 9.58 → 9.66 MB. Growth slows to ≈ 0.05 MB per
   cycle, with GC-timing noise. It is not proportional to what a session
   allocates (a single session holds several MB of views, pools and buffers).
2. **Heap snapshot diff** (unminified build, cycles 2 → 5, objects that are new
   *and* still reachable):
   - **0** `GameSession`, `Simulation`, `GameRenderer`, `ShipView`,
     `EffectsLayer`, `FrameStats` or Pixi `Application` instances survive.
     Every session, with its views, pools, generated textures and listeners,
     is collected.
   - The survivors are about 10 KB of small objects (generators, promises, a
     few `Float32Array`s), retained by two library-level paths:
     - **MSW worker client:** `getWorker → workerPromise → PromiseReaction
       chain → Generator → MessageEvent (request payload)`. Each request the
       service worker forwards leaves a small reaction reachable. One request
       happens per battle cycle.
     - **PixiJS shader program cache** (module scope): `glProgram._uniformData`
       keeps the uniform buffers (`uProjectionMatrix`, `uWorldColorAlpha`,
       `uResolution`…) of programs compiled by earlier renderers.
3. **Conclusion.** No application-level leak: listeners, DOM nodes and
   canvases stay flat, and nothing created by a session outlives it. The
   residual growth is bounded caching inside MSW and PixiJS, a few tens of KB
   per match once warm.

**Possible next steps** (not needed at the current scale): keep one Pixi
`Application` alive across matches instead of one per session, which avoids
recompiling and caching programs per renderer; and, in a real deployment,
serve the API without MSW.

## Limitations

- **One reference machine.** An Apple M2 is a fast GPU and CPU. Low-end
  Android phones were not profiled. Expect the CPU work per frame to be several
  times higher there; it would still fit the budget, but GPU fill rate at high
  DPR (the renderer caps resolution at 2×) is the more likely limit.
- **GPU time is not measured.** The CPU metric covers render *submission*,
  not GPU execution. Frame-time stability (no frame over 17.7 ms) is the
  indirect evidence that the GPU keeps up.
- **Headless.** New-headless Chromium uses the real GPU path and real frame
  scheduling, but no compositor of a visible window. A headed run with the
  DevTools Performance panel was not part of the automated report.
- **Scripted pilot.** It fires constantly but does not aim, so projectiles
  in flight are fewer than in a busy human match (shots expire on islands and
  range). Ships, the main cost, were at the cap for the whole run.
- **Audio** was muted to keep runs deterministic; Web Audio playback runs off
  the main thread and is not expected to change the results meaningfully.
